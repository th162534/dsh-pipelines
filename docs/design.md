# 设计说明

## 定位

本插件只做一件事：把**确定性任务**从对话里搬到进程里。
它不是工作流引擎，不调度专家，不管理长期状态。

## 三层分工

| 层 | 负责 | 例子 |
|---|---|---|
| 流水线 | 结果确定、步骤固定 | 下载、ASR、抽帧、OCR、格式转换 |
| 专家 | 需要判断 | 选题、评价、写结论、改代码 |
| 主会话 | 判断该谁做 | 路由、汇总、与用户对话 |

优先级固定：**流水线 > 专家 > 主会话自己做**。顺序反了会浪费钱。

## 为什么返回体这么小

`pipeline_run` 只回 `runId`、每步状态、产物路径。
一次视频转写动辄几万字，回传等于把上下文预算烧掉；路径让下游按需读取。

## 为什么用声明式步骤

`pipeline.json` 描述「跑什么、超时多久、产物在哪」，脚本只负责干活。
好处：加一条流水线不需要改插件代码；坏处：复杂分支仍要写进脚本。

## 缓存与幂等（路线图）

当前每条流水线自行决定缓存方式（`bili-evidence` 复用 bv.py 的缓存目录）。
后续在 runner 里加「输入 hash + 步骤名」的跨运行缓存，只缓存声明了 `cache: true` 的步骤。

## 与专家体系的关系

专家也可调用 `pipeline_run`，避免「专家再手搓一遍脚本」。
禁止脚本调用专家：脚本只能调用模型判断点（judge），不能反向委派，否则会形成递归。

## 安全边界

- 步骤进程的工作目录固定为流水线目录，产物必须落在本次运行目录内。
- 不把凭据写进命令行；需要时走环境变量。
- 失败即停，保留已完成产物，不自动重试（重试由调用方决定）。
